1. PROJECT MISSION
========================================================================

1.1. Primary mission.

Perform an exhaustive, evidence-led, cross-version and cross-platform investigation of Google Antigravity and its relevant components; reconcile all relevant work already performed by this and other agents across all accessible workspaces and sessions; consolidate artifacts into one canonical MegaDaemon project workspace; reconstruct relevant functionality and protocols; implement the required capabilities in MegaDaemon, primarily in Rust; preserve and improve existing MegaDaemon functionality, including Snatcher; create reproducible tests and documentation; optimize for constrained hardware including Android ARM64; and deliver a complete, auditable result.

1.2. This is not a superficial research task.

The task is not complete merely because you:
- read the README;
- download the latest installer;
- extract a few strings;
- find a community protobuf repository;
- generate Rust structs;
- write a short report;
- create a prototype;
- wrap the original Language Server;
- call an existing SDK;
- create a few RPC methods;
- make one successful demonstration.

The required work includes archaeology, evidence management, version analysis, reverse engineering, protocol reconstruction, behavior testing, architecture, implementation, integration, resource engineering, security, documentation, and delivery.

1.3. Desired end state.

The final MegaDaemon implementation should provide the relevant, justified Antigravity-compatible capabilities as a maintainable, testable, self-contained implementation. The original proprietary Language Server may be used as a controlled reference/oracle during legitimate research and migration, but it must not remain a required runtime dependency of the final implementation.

The final deliverable must not require the original `.so`, original Go executable, proprietary Language Server process, or hidden Antigravity installation for functionality that has been reimplemented.

Do not promise complete parity before measuring it. Explicitly identify unsupported behavior and remaining gaps.

1.4. Preserve the user's established technical constraints.

The target Android environment includes:
- `aarch64-linux-android`;
- Exynos 2100 hardware;
- Android Bionic libc;
- a constrained mobile resource budget.

The following are explicit exclusions for the target architecture unless the main agent obtains a new, explicit user decision:
- no dependency on external Goose binaries;
- no dependency on external Zellij binaries;
- no dependency on external Nushell binaries;
- no JSON-RPC serialization layer for the shared-memory path;
- no `zellij-server`;
- no Wasmtime or Cranelift;
- no `portable-pty`;
- no `nu-cli`;
- no Reedline;
- no unguarded filesystem commands;
- preserve the existing zero-copy `shm.rs` design and its semantics.

These exclusions do not automatically prohibit studying those projects as references. They prohibit silently making the excluded components runtime dependencies or replacing the established architecture with them.

Prior research proposed, among other things, in-process `nu-engine` or a custom `ShmValue`, `nix::pty` plus `vt100` for terminal/session handling, policy-gated runtime patterns, ACP over `/api/ws/acp` and stdio, a cockpit on port 3000, and possibly `kaish`. Treat these as historical proposals, not approved implementation decisions. Re-open the actual artifacts, verify current repository state, evaluate each proposal against the constraints, and record adopt/adapt/reject decisions. Zellij was previously deferred to desktop clients; do not reintroduce it as an Android dependency.

The existing zero-copy shared-memory implementation in `shm.rs` is a protected compatibility boundary. Inspect it before making changes. Do not replace, redesign, serialize around, or degrade it without a demonstrated requirement, benchmark, compatibility plan, and explicit approval.

1.5. Scope of reverse engineering.

Investigate, as applicable and legally permitted:
- Antigravity desktop application;
- standalone IDE;
- CLI;
- SDK;
- extensions and integrations;
- Googlebook / Android distribution;
- Language Server;
- Go binaries;
- protobuf schemas and generated code;
- Blaze-related components;
- ConnectRPC, gRPC, gRPC-Web, HTTP and streaming;
- agent orchestration and session behavior;
- tools and tool schemas;
- Snatcher and other relevant helper tools;
- prompts, templates, resources, embedded files;
- state management and persistence;
- external server interactions observable through authorized testing;
- version differences and platform differences.

4.4. Preserve originals.

Never edit the only copy of an original artifact. Intake procedure:
1. Identify source.
2. Record source location and provenance.
3. Record file metadata.
4. Calculate SHA-256 if bytes are available.
5. Preserve an immutable original copy or a verifiable pointer if copying is prohibited.
6. Create a working copy.
7. Normalize only the working copy.
8. Record every transformation.
9. Link derived artifacts to their parent artifacts.

Do not rename the only original file. Keep its original filename in metadata.

4.5. Artifact identity and provenance.

Each artifact should have a stable artifact ID and a manifest entry with:
- artifact_id;
- original_filename;
- canonical_filename;
- original_location;
- canonical_location;
- source_session;
- source_agent;
- source_task;
- source_repository and commit, if applicable;
- created_at;
- acquired_at;
- modified_at, if known;
- product;
- product_version;
- component_version;
- platform;
- architecture;
- file_type;
- size_bytes;
- sha256;
- signature_status;
- license_status;
- evidence_level;
- trust_status;
- relationship_to_other_artifacts;
- transformation_history;
- notes.

Use a machine-readable format such as JSONL, CSV, SQLite, or TOML after evaluating the existing repository conventions. Do not create several competing registries.

4.6. Duplicate handling.

Detect exact duplicates by cryptographic hash. Distinguish exact duplicates from:
- same name, different bytes;
- same size, different bytes;
- repackaged identical payload;
- same code with different build metadata;
- semantically equivalent but byte-different binaries.

Do not discard provenance when deduplicating. A content-addressed store may retain one physical copy while preserving all source references.

4.7. Quarantine, not deletion.

Incorrect, incomplete, obsolete, contradictory, corrupted, untrusted, or superseded results must be moved or referenced in QUARANTINE/HISTORICAL with a clear status. Do not silently delete them. Never run untrusted scripts or binaries merely to inspect their contents.

5. MULTI-AGENT ORCHESTRATION AND COLLABORATION
========================================================================

5.1. Orchestration model.

The main agent remains the single accountable owner of the final result. Specialists provide bounded research or implementation outputs. A specialist must not silently redefine the project scope.

Prefer manager-led orchestration when the main agent must synthesize results and retain final ownership. Use handoffs when a specialist needs to take ownership of a bounded branch. Use parallel agents only for genuinely independent tasks.

Do not create agents merely to increase their number. Create them when they have distinct tools, expertise, context, or deliverables.

5.2. Agent capability discovery.

The main agent must inspect:
- native agent creation;
- subagent handoffs;
- task delegation;
- agent-as-tool patterns;
- shared context;
- persistent sessions;
- workspace mounting;
- tool permissions;
- agent monitoring;
- cancellation;
- result retrieval;
- approval gates;
- concurrency limits.

If the platform has a native workflow, use it rather than inventing a parallel system. If no orchestration API exists, use a documented manual queue and sequential specialist runs.

5.3. Proposed workstreams.

The following are workstreams, not a mandatory fixed count of agents. The main agent may combine or split them based on capacity.

W00 - MAIN PROGRAM DIRECTOR / CHIEF INTEGRATOR
Owns scope, canonical workspace, task registry, dependencies, priorities, resource budget, decisions, integration, final review and user reporting.

W01 - WORKSPACE AND SESSION ARCHAEOLOGY
Finds all relevant workspaces, sessions, repositories, agent outputs, attachments, file-library records, archives and previous deliverables. Produces census, provenance manifests and intake package.

W02 - REPOSITORY AND CODEBASE AUDIT
Audits actual MegaDaemon repository, history, branches, worktrees, modules, APIs, tests, build system, current architecture and uncommitted changes.

W03 - ANTIGRAVITY RELEASE ARCHAEOLOGY
Enumerates official products, releases, installers, changelogs, platform packages and version boundaries. Verifies package provenance and hashes.

W04 - WINDOWS ANALYSIS
Analyzes Windows installer and PE binaries, x64 and ARM64, resources, dependencies, signing, processes and IPC.

W05 - LINUX ANALYSIS
Analyzes Linux packages and ELF binaries, x86_64 and ARM64, dependencies, packaging and runtime behavior.

W06 - macOS ANALYSIS
Analyzes Mach-O, Apple Silicon and Intel packages, frameworks, signing, entitlements, resources and process behavior.

W07 - ANDROID / GOOGLEBOOK ANALYSIS
Determines the actual product and compatibility boundaries, package identity, Android ABI, Bionic compatibility, Googlebook requirements and mobile runtime behavior. Must honor the user's target environment and exclusions.

W08 - GO LANGUAGE SERVER REVERSE ENGINEERING
Analyzes Go metadata, function tables, symbols, types, packages, control flow, resources and version differences.

W09 - PROTOBUF / SCHEMA RECOVERY
Extracts descriptors, messages, services, enums, fields, oneofs, source information and generated-code structures.

W10 - BLAZE / CONNECTRPC / TRANSPORT

W11 - AUTHENTICATION AND SESSION FLOW
Investigates authentication, session creation, state, refresh, errors and all unresolved control flow. Must preserve explicit unknowns.

W12 - BEHAVIORAL ORACLE AND DIFFERENTIAL TESTS

W13 - TOOLING AND SNATCHER

W14 - MEGADAEMON ARCHITECTURE

W15 - RUST IMPLEMENTATION

W21 - DOCUMENTATION / RELEASE / DRIVE DELIVERY

14. MEGADAEMON ARCHITECTURE AND RUST IMPLEMENTATION
========================================================================

14.1. Audit before design.

Map current code and existing contracts. Do not assume the repository matches previous reports. Previous proposals are hypotheses until verified against the current commit.

14.2. Adopt / adapt / reject process.

For every proposed library, architecture, subsystem or prior artifact, make an explicit decision:
- ADOPT: use with minimal changes;
- ADAPT: reuse but modify;
- REIMPLEMENT: build a compatible implementation;
- REJECT: unsuitable;
- DEFER: potentially useful but not currently justified;
- RESEARCH: insufficient evidence.

Record rationale, license, maintenance, security, Android compatibility, resource use, API stability, dependencies and benchmark evidence.

14.3. Rust design.

Prefer:
- explicit ownership;
- bounded allocations;
- structured errors;
- small cohesive modules;
- stable traits/interfaces;
- deterministic tests;
- bounded concurrency;
- explicit cancellation;
- bounded channels;
- backpressure;
- zero-copy where demonstrably beneficial;
- minimal justified dependencies;
- reproducible generated code.

Avoid:
- unnecessary clones;
- unbounded queues;
- unbounded caches;
- excessive dynamic dispatch;
- blocking work on async executor threads;
- hidden global mutable state;
- unsafe code without a documented safety argument;
- abstraction layers without a clear purpose;
- frameworks that duplicate existing functionality.

14.4. No automatic Rust absolutism.

Rust is the primary implementation language, but a small C/assembly/platform shim may be justified if it is required for ABI compatibility, performance or operating-system integration. Such exceptions must be minimal, documented, tested and approved. Do not use foreign-language components to smuggle in prohibited runtime dependencies.

14.5. Preserve shared-memory design.

Inspect `shm.rs`, document its memory layout and invariants, add tests before modifying it, and preserve zero-copy semantics. Any layout change requires versioning, compatibility tests, migration and approval. Do not introduce JSON-RPC serialization for shared-memory values.

14.6. Android-specific build and runtime.

Verify the Rust target, NDK, API level, linker, Bionic, atomic support, filesystem semantics and shared-memory behavior. Test on the actual target device where available; emulator results are not a substitute for Exynos 2100 measurements.

14.7. Terminal and scripting.

Investigate the existing implementation and previous proposals. A possible in-process scripting approach or PTY implementation must be evaluated against current code and explicit exclusions. Do not introduce external Goose, Zellij or Nushell executables, `zellij-server`, Wasmtime/Cranelift, `portable-pty`, `nu-cli`, Reedline or unguarded filesystem execution. Do not assume `nix::pty`, `vt100`, `nu-engine`, custom `ShmValue`, ACP or `kaish` are approved; validate them as candidates and document decisions.

14.8. Generated code.

Generated code must have:
- source schema;
- generator name and version;
- pinned generator;
- generation command;
- output hash;
- reproducible result;
- clear separation from handwritten code;
- tests;
- license/provenance record.

15.3. Critical NFS rule.

SQLite WAL requires participating processes to be on the same host and does not work over a network filesystem. SQLite also warns that broken network filesystem locking can corrupt databases. Do not put a live SQLite WAL database on NFS and claim it is safe.

Use local storage for active database state. Use NFS or remote storage for immutable artifacts, backups, controlled exports or a properly designed client/server or replication layer.

15.4. Durable job execution.

Persist job state and checkpoints. Define idempotency keys, retry policy, lease/ownership, cancellation, deadlines, recovery and dead-letter handling. A process restart must not cause duplicate destructive side effects.

15.5. Atomicity and corruption recovery.

Use atomic file replacement where supported, fsync according to durability requirements, checksums, integrity checks, schema migrations, backup verification and quarantine. Do not claim durability without testing crash/power-loss scenarios relevant to the platform.

16. PERFORMANCE, RESOURCE BUDGETS AND SCHEDULING

16.1. Baseline first.

Cargo build jobs reference:
https://doc.rust-lang.org/stable/cargo/commands/cargo-build.html

16.2. Conservative scheduling.

Start with low concurrency. Use `cargo -j1` as a conservative baseline when building on a constrained host, then raise only after measurement. Do not assume logical CPU count equals safe parallelism.

16.3. Heavy-job controls.

Limit concurrent:
- Ghidra analyses;
- bulk extraction;
- full builds;
- fuzzing;
- large test suites;
- indexing;
- benchmark runs;
- decompilation;
- large downloads.

Use local SSD for worktrees, Cargo target directories, temporary databases and analysis indexes when available. Avoid heavy small-file workloads on NFS.

16.4. Adaptive load shedding.

Pause or reduce low-priority work when:
- memory pressure rises;
- swap thrashing occurs;
- I/O stalls rise;
- NFS latency degrades;
- disk approaches capacity;
- thermal throttling occurs;
- battery constraints require it;
- interactive responsiveness degrades.

Use measured host-specific thresholds. Do not invent universal numeric limits.

16.5. Resource ledger.

Record per task:
- CPU time;
- wall time;
- peak RSS;
- disk read/write;
- output size;
- network bytes;
- process/thread count;
- temperature/battery impact when available;
- failures and retries.

16.6. Mobile performance.

Measure cold start, warm start, idle memory, peak memory, sustained CPU, battery drain, thermal throttling, storage I/O and recovery after process death on the actual target where possible.

20. EVIDENCE, CONFIDENCE AND ANTI-HALLUCINATION POLICY
========================================================================

20.1. Evidence statuses.

Use:
VERIFIED
STRONGLY_SUPPORTED
INFERRED
UNKNOWN
NOT_VERIFIED
CONTRADICTED
NOT_APPLICABLE

20.2. Evidence levels.

LEVEL A - direct primary evidence:
- official source;
- binary or descriptor extracted from a verified package;
- reproducible experiment;
- direct authorized observation;
- source code at a pinned commit.

LEVEL B - independent corroboration:
- multiple independent sources that agree;
- independently reproduced behavior.

LEVEL C - indirect evidence:
- strings;
- symbols;
- call graph;
- metadata;
- inferred control flow;
- community schema matching part of a binary.

LEVEL D - hypothesis:
- plausible but unverified interpretation;
- incomplete snippet;
- undocumented assumption.

20.3. Citation rules.

For every web-derived factual claim:
- cite the source;
- provide the full plaintext URL in the documentation;
- record access date;
- record publication/release date where relevant;
- quote only what is necessary;
- distinguish vendor statements from observed facts;
- note when a page is mutable.

For every file-derived claim:
- cite artifact ID and hash;
- include file path and line/page/offset when possible.

For every binary-derived claim:
- include binary hash;
- version;
- architecture;
- address/offset;
- tool and version;
- extraction method.

For every behavioral claim:
- include fixture/test ID;
- environment;
- request/response or sanitized trace;
- repeatability status.

20.4. Contradictions.

Do not resolve contradictions by choosing the more convenient source. Create a contradiction record containing:
- claim A;
- claim B;
- sources;
- versions;
- scope;
- possible explanation;
- tests needed;
- current status.

20.5. No false completeness.

A percentage must have a defined denominator. A statement such as "all RPCs recovered" requires a defensible method for establishing the complete RPC universe. If the universe cannot be known, say so.
